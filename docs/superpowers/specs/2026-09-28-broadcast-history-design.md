# История рассылок и уведомлений + докат недостающим

Дата: 2026-09-28

## Контекст

Сейчас в админке два похожих канала массовой отправки — Telegram-рассылки
(«Бот» → «Рассылки», пишет в `bot_outbox`) и внутриприкладные уведомления
(«Уведомления», пишет в `notifications`/`notification_recipients`). Оба
устроены одинаково: получатели материализуются **один раз, в момент
отправки** — это осознанное решение из прошлых дизайнов
([[bot-messages-design]], [[notifications-design]]), и оно остаётся верным.
Проблема в другом: обе таблицы **уже хранят** полную историю по
получателям, но админка никогда не читает её обратно (`ucimo_admin_ro`
сейчас только `INSERT` на эти таблицы) — ни списка прошлых отправок, ни
способа понять, кто не попал в конкретную рассылку.

Конкретный кейс Гриши: разослал сообщение в Telegram, после этого
зарегистрировались новые пользователи — и сейчас нет способа увидеть, что
рассылка вообще была, и отправить её тем, кто её не получил (потому что
их ещё не было в базе на момент отправки).

Это не про статус доставки Telegram и не про «прочитано» у уведомлений —
это отдельные вещи. «Не получил» здесь означает буквально «не входил в
список получателей этой рассылки/уведомления», что и есть корень
описанной проблемы.

## Архитектура

```
                     ┌─ GET /broadcasts ──────────► история (текст, дата, N получателей)
ucimo-content-admin  │
 «Бот»→«Рассылки»  ──┼─ GET /broadcasts/:id/missing ► кандидаты минус уже получившие эту рассылку
 (ProdDbService)      │
                     └─ POST /broadcasts (как раньше, + INSERT broadcasts) ──► bot_outbox.broadcast_id

                     ┌─ GET /notifications ───────► история (текст, дата, N получателей)
 «Уведомления»     ──┼─ GET /notifications/:id/missing ► кандидаты минус уже получившие это уведомление
 (ProdDbService)      │
                     └─ POST /notifications (без изменений)
```

Оба списка истории и «missing»-запросы — read-only чтение уже
существующих (для уведомлений) или почти существующих (для рассылок,
плюс одна новая таблица-группировка) данных. Никакой новой логики
отправки, воркеров или изменений в Go-рантайме serbian-app не требуется —
`bot_outbox`-воркер и `ListNotificationsForUser` продолжают работать как
прежде, лишний столбец/таблицу они просто не видят.

## Схема данных (serbian-app) — миграция `012_broadcast_history.sql`

```sql
-- Группирует строки bot_outbox, у которых сейчас нет стабильного id —
-- только случайно совпадающие text/created_at в рамках одной отправки.
-- Реминдеры и /start-ответы broadcast_id не получают (остаётся NULL) —
-- это не рассылки.
CREATE TABLE IF NOT EXISTS broadcasts (
	id         {{.AutoID}},
	text       TEXT NOT NULL,
	created_at TEXT NOT NULL
);

ALTER TABLE bot_outbox ADD COLUMN broadcast_id BIGINT;
CREATE INDEX IF NOT EXISTS bot_outbox_broadcast_idx ON bot_outbox (broadcast_id);
```

`BIGINT`, not `INTEGER` — matches what `{{.AutoID}}` actually expands to for
`broadcasts.id` on Postgres (`BIGINT GENERATED BY DEFAULT AS IDENTITY`; see
`011_donations.sql` for the same portable-`BIGINT`-column precedent). Follow
through in the admin: `node-pg` returns `bigint` columns as JS **strings**
(precision safety), so `broadcasts.id`/`bot_outbox.broadcast_id` are handled
as `string` in TypeScript end to end — same convention already used for
`notifications.id` in `notifications.service.ts`'s `RETURNING id`.

`notifications`/`notification_recipients` — без изменений схемы, они уже
несут id и по строке на получателя.

`broadcast_id` — обычная колонка без `REFERENCES` (как и
`notification_recipients.notification_id` в 010-й миграции — в этой схеме
внешние ключи между такими таблицами нигде не форсируются на уровне БД).

## Права на проде

Прибавка к уже выданным грантам (не отменяет их):

```sql
GRANT SELECT, INSERT ON broadcasts TO ucimo_admin_ro;
GRANT SELECT ON bot_outbox TO ucimo_admin_ro;              -- INSERT уже есть с 2026-09-22
GRANT SELECT ON notifications TO ucimo_admin_ro;           -- INSERT уже есть с 2026-09-23
GRANT SELECT ON notification_recipients TO ucimo_admin_ro; -- INSERT уже есть с 2026-09-23
```

`broadcasts.id`/`notifications.id` — `GENERATED BY DEFAULT AS IDENTITY`;
отдельный грант на sequence не нужен (Postgres не требует привилегий на
sequence для identity-колонок, в отличие от `serial`) — тот же режим, что
уже работает для `INSERT ... RETURNING id` в `notifications`.

Применяется руками через psql после того, как миграция 012 создаст
таблицу/колонку на проде — тем же процессом, что и предыдущие гранты.

## Го-изменения (serbian-app)

Нет. Миграция самодостаточна (воркер `bot_outbox` и чтение уведомлений
игнорируют новый столбец/таблицу), никакой Go-код правкам не подлежит.

## Эндпоинты и Frontend (ucimo-content-admin)

### `broadcasts`-модуль

- `BroadcastsService.send()`: перед вставкой в `bot_outbox` сначала
  `INSERT INTO broadcasts (text, created_at) VALUES ($1, $2) RETURNING id`
  (используя тот же `createdAt`, что раньше шёл только в `bot_outbox`);
  дальше каждая строка `bot_outbox` получает этот `broadcast_id`. Ничего
  не создаётся при `dryRun` или пустом списке получателей — как сейчас.
- Новый `BroadcastsService.list(): Promise<BroadcastHistoryEntry[]>`:
  ```sql
  SELECT b.id, b.text, b.created_at,
         COUNT(o.id) AS recipient_count
  FROM broadcasts b
  LEFT JOIN bot_outbox o ON o.broadcast_id = b.id
  GROUP BY b.id, b.text, b.created_at
  ORDER BY b.created_at DESC
  ```
- Новый `BroadcastsService.missing(id: number): Promise<BroadcastCandidate[]>`:
  берёт `candidates()` (как сейчас — все с привязанным Telegram) и
  вычитает тех, чей `chatId` уже встречается в
  `SELECT chat_id FROM bot_outbox WHERE broadcast_id = $1`.
- `BroadcastsController`: `GET /broadcasts` → `list()`;
  `GET /broadcasts/:id/missing` → `missing(id)` (id не число → 400,
  несуществующий id → пустой список, не 404 — как и `candidates`, не
  критичная операция).

### `notifications`-модуль (зеркально)

- `NotificationsService.list(): Promise<NotificationHistoryEntry[]>` —
  тот же JOIN-запрос над `notifications`/`notification_recipients`.
- `NotificationsService.missing(id: number): Promise<NotificationCandidate[]>` —
  `candidates()` (все пользователи) минус те, у кого уже есть строка в
  `notification_recipients WHERE notification_id = $1`.
- `NotificationsController`: `GET /notifications`, `GET /notifications/:id/missing`.
- `send()` не меняется — `notifications.id` и так уже возвращался
  (`RETURNING id`), просто раньше нигде не использовался дальше.

### Типы (`web/src/types.ts`)

```ts
export interface BroadcastHistoryEntry {
  id: number;
  text: string;
  createdAt: string;
  recipientCount: number;
}
export interface NotificationHistoryEntry {
  id: number;
  text: string;
  createdAt: string;
  recipientCount: number;
}
```

### `BroadcastsView.vue` / `NotificationsView.vue`

Композер (форма отправки) остаётся сверху и не меняется. Под ним —
новый блок «История»:

- Список отправок: дата, текст (обрезан до ~80 символов, полный текст —
  в `title`), «Получателей: N».
- Клик по строке разворачивает её и **один раз** (кэшируется в локальном
  `ref`-словаре по id) запрашивает `GET .../:id/missing` — грузить это
  для всех строк сразу при открытии страницы не нужно, это N лишних
  запросов почти всегда ради данных, которые никто не откроет.
- Если `missing.length === 0` — «Все получили», кнопки нет.
- Иначе — «Не получили: M» + кнопка «Отправить недостающим»: подставляет
  в композер `text = entry.text`, `sendToAll = false`,
  `selectedIds = missing.map(c => c.id)`, скроллит к началу страницы.
  Дальше — **тот же самый** флоу dry-run → модалка подтверждения →
  `POST`, что и у обычной отправки: получившийся список получателей можно
  доправить руками перед отправкой, ничего специального под «повторную»
  отправку не заводится (она просто создаёт новую строку в
  `broadcasts`/`notifications`, как обычная).

## Тестирование

- **serbian-app**: только гард на то, что миграция 012 применяется на
  обоих диалектах — `go test ./server/internal/store/...`, `make test-pg`.
  Новых поведенческих тестов нет (Go-код не меняется).
- **ucimo-content-admin**:
  - `broadcasts.service.spec.ts` (расширить, тесты через реальный Postgres
    по образцу уже существующих для `bot-messages`/`links`, без моков):
    `send()` создаёт строку в `broadcasts` и простав­ляет `broadcast_id`
    всем строкам `bot_outbox` этой отправки; `list()` отдаёт верный
    `recipientCount`; `missing()` возвращает пусто сразу после отправки
    «всем» и возвращает нового кандидата, добавленного (руками, INSERT в
    тестовую фикстуру identities/users) после отправки.
  - `notifications.service.spec.ts` — та же тройка тестов над
    `notifications`/`notification_recipients`.
  - `broadcasts.controller.spec.ts` / `notifications.controller.spec.ts`:
    `GET /broadcasts/:id/missing` с нечисловым `id` → 400; без прод-БД →
    503 (по образцу существующих тестов на `POST`).
  - Фронт: компонентный тест на `BroadcastsView.vue` — клик по строке
    истории один раз вызывает `missing`-запрос (повторный клик — не
    вызывает снова, кэш), клик «Отправить недостающим» заполняет
    композер ожидаемыми `text`/`selectedIds`.

## Вне скоупа

- Статус доставки Telegram (`bot_outbox.status`) и «прочитано»
  (`notification_recipients.read_at`) в истории не показываются — это
  сознательно другая ось, не то, что просили.
- Редактирование/удаление прошлой рассылки или уведомления из истории.
- Автоматическая фоновая докатка новым пользователям без участия
  админа — только ручное «Отправить недостающим» по кнопке.
- Пагинация списка истории — пока рассылок/уведомлений мало, YAGNI, как
  и с остальными не-`Page`-списками в этой админке до появления реальной
  потребности.
- Объединение UI рассылок и уведомлений в один экран — они остаются
  двумя разными разделами сайдбара, просто с одинаковым паттерном внутри.
