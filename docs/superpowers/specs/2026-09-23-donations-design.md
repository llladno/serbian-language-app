# Donations (Tribute) — design

## Goal

Let users support the project financially via Tribute (донат-тариф "Šoljica kafe"), from a new entry point at the bottom of the profile page. Every donation must be visible with donor identity (where resolvable) and amount in a new admin section — this is the hard requirement driving the data model below.

Explicitly out of scope: subscriptions/recurring billing as a feature we build (Tribute's own recurring-donation events are still logged if they arrive, but we don't build UI around them), amount selection in our own UI (Tribute's payment page handles that), Boosty/YooMoney/Stars (may come later, not part of this feature).

## Entry points (confirmed with Tribute's author panel)

- Telegram (Mini App): `https://t.me/tribute/app?startapp=dQWl`
- Web (no Telegram required): `https://web.tribute.tg/d/QWl`

Both are fixed, pre-created links for the "Šoljica kafe" donation tier — not derived from an API call at runtime.

## Frontend (`web/`)

**Placement:** new `DonateCard.vue`, rendered in `ProfileView.vue` directly below the existing `<SupportCard v-if="me" />`. Same structural role as `SupportCard` (icon + short copy + button), icon is the heart PNG asset.

**Click behavior on the card's button:**
- `isTelegram()` (existing helper, `src/telegram.ts`) → open `TRIBUTE_TELEGRAM_LINK` directly, no modal (mirror the `window.open(url, '_blank')` pattern used in `lib/telegramStart.ts`; verify manually inside an actual Telegram Mini App session that this behaves as a same-app handoff rather than a popup — WebView popup behavior can differ from a normal browser and is worth a manual check during implementation)
- otherwise → open `DonateModal`

**`DonateModal.vue`:** copy the `Teleport to="body"` + `Transition name="modal-overlay"` structure from `SupportModal.vue`. Contents: `support-bird.png` image, short "Šoljica kafe" copy (already drafted in chat — reuse it), two buttons as plain `<a target="_blank" rel="noopener">` (same pattern as `SupportModal`'s Telegram link):
- "Поддержать через телеграм" → `TRIBUTE_TELEGRAM_LINK`
- "Поддержать" → `TRIBUTE_WEB_LINK`

**`web/src/lib/donateModal.ts`:** new composable, module-level `ref` for open/close state (same shape as `supportModal.ts`'s `useSupportModal()`), plus:
```ts
export const TRIBUTE_TELEGRAM_LINK = 'https://t.me/tribute/app?startapp=dQWl'
export const TRIBUTE_WEB_LINK = 'https://web.tribute.tg/d/QWl'
```
Hardcoded constants, no env var — matches how `SUPPORT_TELEGRAM_URL` is defined today (project has no i18n/config-injection system for this kind of value).

Mount `DonateModal` once in `AppNav.vue` alongside the existing `SupportModal` mount.

**Assets (provided by user, not generated by this task):**
- `web/src/assets/donate/heart.png` — icon on `DonateCard`
- `web/src/assets/donate/support-bird.png` — image inside `DonateModal`

## Backend (`server/`)

**Config** (`internal/config/config.go`): add `TributeAPIKey string`, loaded via `os.Getenv("TRIBUTE_API_KEY")`. Set as a Dokploy env var in prod, never committed.

**Webhook receiver** — new `internal/api/tribute.go`, route `POST /api/tribute/webhook` registered in `api.go`'s `Handler()`, same style as the existing `POST /api/telegram/webhook`:
- Add to the CSRF `checkOrigin` exemption list in `middleware.go` (Tribute is server-to-server, sends no Origin/Referer, same reasoning as the Telegram webhook exemption).
- Verify the `trbt-signature` header: HMAC-SHA256 of the raw request body, keyed with `TributeAPIKey`, compared with `hmac.Equal` (constant-time). Model this on the real HMAC verification already in `internal/auth/telegram.go` (`hmacSHA256`/`VerifyInitData`) rather than the Telegram webhook's plain string-compare — Tribute's is a real per-request signature, not a static shared secret.
- Parse the JSON body for: event type (`newDonation`, `recurrentDonation`, `cancelledDonation` handled; other event types logged and ignored), donor `telegram_user_id`, `telegram_username` if present, amount, currency. Store the full raw body alongside the parsed fields (see data model) so we aren't blocked by fields we didn't anticipate.
- Resolve `user_id` via `Store.IdentityByProviderUID("telegram", telegramUserID)` — donors are not required to have an account in our system, so this may come back empty; that's fine, `donations.user_id` is nullable.
- Always return 200 once the row is durably written (Tribute retries with backoff on non-200/timeout — see idempotency note below).

## Data model

New migration `internal/store/migrations/011_donations.sql`, same shape/conventions as `support_messages` (`005_support_messages.sql`):

```sql
CREATE TABLE donations (
    id                 {{.AutoID}},
    user_id            TEXT,
    telegram_user_id   TEXT NOT NULL,
    telegram_username  TEXT,
    amount_minor_units BIGINT NOT NULL,
    currency           TEXT NOT NULL,
    event_type         TEXT NOT NULL,
    tribute_event_id   TEXT NOT NULL,
    raw_payload        TEXT NOT NULL,
    created_at         TEXT NOT NULL
);
CREATE UNIQUE INDEX donations_tribute_event_id_idx ON donations(tribute_event_id);
```

- `amount_minor_units` — integer, smallest currency unit (kopecks/cents), not a float — avoids rounding drift when the admin view sums donations.
- `tribute_event_id` + unique index — dedupes Tribute's retried webhook deliveries (insert becomes a no-op on conflict) so a retried delivery can't double-count a donation.

## Open questions to confirm during implementation

Tribute's public docs describe the webhook's signature scheme and event type names but don't publish a full example JSON payload. Before writing the handler, confirm against a real test event (Tribute's author panel likely has a "send test webhook" option, otherwise the first real donation):
- Exact field name and casing for the donor's Telegram id and for amount/currency (assumed `telegram_user_id`, but not verified character-for-character).
- Whether `amount` arrives already in minor units or major units — `amount_minor_units` above assumes we may need to multiply by 100; adjust the parsing (not the schema) if Tribute already sends minor units.
- The field to use as `tribute_event_id` for the dedupe index (a top-level event/delivery id is assumed to exist; if not, fall back to a hash of the raw body).

## Admin view

Lives in `ucimo-content-admin` — see that repo's `docs/superpowers/specs/2026-09-23-donations-design.md`. Reads this repo's `donations` table directly over Postgres (same pattern as `support_messages`), no new API surface needed here beyond the webhook itself.
